以 remotion-video/ 的实际代码、测试、台账与产物为依据，逐条列出工作流与产品的不足，并给出可执行的整改建议。

一句话结论：这个项目的规范写得比代码好，测试写得比规范窄。 SKILL.md 已经把"什么是对的"定义得相当完整，但规则几乎全靠人工执行；而唯一被机器强制的那部分（黑名单词），恰恰是事后补救性质的。 于是出现三个断层：规范没有执行层、内容与排版焊死在一起、全部资产没有版本控制与备份。

共享壳层改动的验证方式

既然 55 部影片都渲染自同一个 FinishedFilm，改共享层就必须证明"输出没变"，不能靠感觉。做法是改前改后各渲染一次同一部影片比对字节：

DanshaFirstFilm 改前 md5 241a999e669caf0dfbb45d18ee68e2a5
改后 md5 241a999e669caf0dfbb45d18ee68e2a5 → 完全一致

结论：FinishedFilm 的场景数泛化对已发布影片零影响。这个"重渲染比对哈希"应当成为今后任何共享层改动的标准动作。

脚手架不能把仓库搞红：draft 状态

写完 npm run new-film 后发现一个设计陷阱：脚手架故意产出带 TODO 的未完成影片，而闸门与测试会扫描 src/finished/——也就是说，用一次脚手架就把测试搞红。一个"用一次就破坏 CI"的工具不算工具。

于是把"未完成"做成机器可判定的状态：内容模块仍含 TODO 的数据化影片是 draft。

命令对 draft 的行为
npm run gen不注册 → 没有 Composition → 不可渲染、不可发布
npm run verify直接拒绝，报"still a draft"
npm run check报 draft 行，退出码 0
npm run progress不计入 done，该条目保持 todo
npm test跳过成品断言；另有一条测试断言 draft 绝不出现在 Composition.tsx 里

关键在于最后一行：draft 是严格更弱的状态——放宽容忍度的前提是 draft 根本渲染不出来。因此"能渲染的必然合规"这条约束仍然闭合，draft 不是绕过闸门的后门。

PART 1工作流诊断

整条流水线可以画成这样——红色环节是"规则存在但机器不检查"的位置：

选条目（progress.json）→ 查古籍原文（rg）→ 找授权配图→ 手写 303 行 TSX→ 手工核对文案/字号/重叠→ npm test→ 人工看 3 张静帧→ 渲染 mp4→ 手写上传文案
P0W1 · 合规规范只写在文档里，没有执行层
现象

SKILL.md 在 2026-09 被追加了一整套最关键的合规条款：功效句必须写成 古籍称其主……、注释块必须带 此为汉代认知，未经现代科学证实、现代疗效动词一律不得出现在今译/注释中。但实测 55 部影片里，0 部实现了新框架。

为什么没被执行

因为唯一的"看门测试"是 tests/herbal-short-video-skill.test.mjs——它校验的是 SKILL.md 这个文件里有没有出现某几个字符串，而不是影片里有没有落实这些规则。也就是说，测试保护的是文档的措辞，不是产品的合规性。把 SKILL.md 删掉一半、只要保留关键词，测试依然全绿。

影响

这正是平台已经处罚过的那一类问题。规范升级了，风险却没下降——账号还在养号期，而 44 部存量影片仍在用旧式 主治 表述，且没有任何机制阻止新片继续沿用旧写法（因为新框架没进测试）。

建议
  • 把校验对象从"文档"改成"影片"：新增 tests/compliance.test.ts，扫描每部影片的今译块——功效句必须以 古籍称其主 开头，且注释块必须含免责句。
  • 把黑名单词测试升级为"框架测试"：黑名单是事后拦截，框架是事前约束，后者才可长期维持。
  • 先做一部样板片（黄芝）跑通口径，再批量整改 44 部。
P0W2 · 内容与排版焊死，导致 55 份近似克隆
现象

每部影片是一个 ~303 行的 TSX 文件，其中真正属于"这部片子"的内容只有十几个字符串，其余全是内联样式。归一化后，54 部影片的布局几何只有 9 种签名，最大同构簇 36 部、次大 11 部；每部片有 11–14 个绝对定位块，坐标全部手写。

影响
  • 整改成本爆炸：要把 44 部影片的今译改成新框架，等于改 44 个 TSX 文件里的字符串与样式，而不是改一处数据。
  • 可读性失控：全项目散落 46 种字号（14、15、19、20、21、22、23、24、25…），相邻值成堆，说明字号是逐个手调出来的，没有刻度。
  • 重叠风险靠人肉兜底：SKILL.md 专门用一整段叮嘱"要估算每个块的高度、留 50px 间隙、绝不允许两个绝对定位块重叠"——这段叮嘱存在的原因，就是没有布局系统。
  • 无法做 A/B：想试新排版只能复制一份 300 行文件。
建议
  • 把影片拆成"数据 + 渲染器"：新增 src/films/<kebab>.ts 只放内容（条目名、卷次、原文、今译、注释、事实条、配图、音乐、强调色、版式编号），由 <EntryFilm data={...} layout="A" /> 统一渲染。影片文件从 300 行降到约 20 行。
  • 收益是连锁的：整改 44 部 = 改数据；合规校验可以机器化（数据是结构化的）；版式可迭代；可批量重渲染。
  • 同时建立字号刻度（建议收敛到 8 级左右）与布局栅格，把散落的 top 坐标收进版式常量。
P0W3 · 全部资产几乎没有版本控制，也没有备份
现象

git ls-files 只有 11 个文件，全部提交历史只有 1 条（"Create new Remotion video"）。未跟踪的是：src/finished/（55 部影片）、public/（53 张授权图 + 2 首 BGM + credits.json）、tests/、scripts/、progress.json、upload/。没有配置 remote。

更关键的是 .gitignore 忽略了 out/，而 54 部母版 mp4 只存在于这块磁盘上。

影响

upload/_incidents.md 自己写着"55 集母版（out/ + src/finished/）完好，仅平台副本被删"——也就是说母版是唯一副本。同时，credits.json 是图片授权的法律凭据，它和 src/finished/ 一样从未提交，一旦丢失无法重建。

没有版本历史还意味着：无法 diff、无法回滚、无法定位"哪一版改动引入了问题"。

建议
  • 立刻 git add -A 纳入影片、图片、音乐、测试、脚本、台账，并做一次初始提交。
  • 配置私有 remote 并 push，形成异地备份。
  • 母版 mp4 单独备份（对象存储 / 网盘），或在仓库内保留一份 out/ 的校验清单（文件名 + 大小 + 时长 + 帧数）以便核对完整性。
  • 此后再动代码，按"一部影片一次提交"的粒度提交，让历史具备可读性。
P1W4 · 测试用魔法数字锁计数，每加一个资源就要改测试
现象

测试里写死了 assert.equal(ledger.length, 53)（credits.json 条数）、assert.ok(images.size > 40)、assert.ok(finishedFiles.length > 50)。

影响

新增第 54 张配图就会让测试变红，而失败原因与"图片有没有授权"毫无关系。这会训练出一种坏习惯：看到红灯先改数字。久而久之测试失去信号价值——而 W1 的合规规则正是被这种"改测试比改产品省事"的惯性绕过去的。

建议
  • 把计数断言改为派生式：credits.json 条数应与 public/images/ 下实际图片数一致；引用的图片集合应与台账集合互为子集。
  • 数量下限断言只保留 1–2 个粗粒度守卫（例如"至少 1 部影片"），不作为精确约束。
P1W5 · 同一个事实在四个地方手工维护，命名靠字符串启发式
现象

要新增一部影片，需要同时改：scripts/build-progress.mjs 里的 DONE 映射表、progress.json（由脚本生成）、tests/finished-video.test.ts 里的 shangjingContinuation 表格行、upload/<kebab>.md 台账，以及 src/finished/<kebab>.tsx 本身。

而"文件名 → 组件名 → Composition id"的映射是靠字符串切分推导的（toComp 把 kebab 按 - 拆开再首字母大写）。这直接导致 angelica-fourth-film-real-photo 这个"包装片"必须在 三个不同文件里各写一次特例排除（测试、生成脚本、progress 脚本）。

影响

信息分散 + 启发式推导 = 命名漂移。脚本自己都在报警：name drift: ... (expected ...tsx)。这类不一致不会立刻报错，只会在某天以"某部片没进台账"的形式暴露。

建议
  • 确立单一事实来源：把条目名、卷次、Composition id 显式声明在影片数据里（配合 W2 的数据化），progress.json 与测试表格都由它派生，而不是反向手工维护。
  • 取消 toComp 这类命名启发式，改为显式映射。
  • 把"包装片"从特例升级为显式字段（例如 wrapperOf: "AngelicaFourthFilm"），三处排除逻辑自然消失。
P1W6 · 质量闸门深度不足：抽 3 帧、只看容器规格、没有 CI
现象

scripts/verify-film.mjs 每部片只渲染 3 张静帧（hero / source / closing），ffprobe 只校验 1080x1920、30fps、H.264、AAC 四项容器规格。没有 CI，npm test 全靠手动。

影响
  • 3 帧 / 360 帧 = 0.8% 采样，而这部产品的核心失败模式恰好是"中间某段文字挤在一起"。
  • 容器规格通过 ≠ 内容正确：音乐有没有真的混进去、音量是否过低、时长是否符合预期，都不在检查范围。
  • 没有 CI，意味着"忘了跑 npm run gen""忘了更新台账"这类错误只能靠人发现。
建议
  • 把静帧抽样加密到每 15 帧一张（约 24 张/片），拼成 contact sheet 供一次性目检；成本远低于逐帧，覆盖面提升 8 倍。
  • 若完成 W2 数据化，可直接从布局常量计算各块包围盒，做自动重叠检测，彻底替代"人眼看 3 帧"。
  • verify 增加：时长与 durationInFrames/fps 一致、音轨存在且非静音、文件大小落在合理区间。
  • 接入 CI（至少 npm test + npm run lint + 校验 Composition.tsx 与 src/finished/ 同步），把"忘记跑命令"从人的责任变成机器的责任。
P2W7 · 文档重点保护的是一层死代码
现象

SKILL.md 反复强调"不要为了一部影片修改 HerbalFeature / HerbProfileTemplate / FormulaShortTemplate"。但实测这三个模板没有任何影片引用，它们只是作为 3 个额外 Composition 挂在 Studio 里；配套的 RootIllustration（代码绘制根茎插画）也已被规则禁止使用。

影响

真正的共享层是 finished-shell.tsx + herbal-stage.tsx + herbal-cards.tsx，但规范里对"这一层该怎么演进"几乎没有约束；而规范花大力气保护的那层没人用。结果是该冻结的没冻结，该演进的没指引。

建议
  • 确认模板确实无引用后归档（移入 legacy/ 或删除），并同步更新 SKILL.md 与 tests/visual-style.test.ts 中针对模板的断言。
  • 把"模板隔离"条款重新指向真正的共享层：SceneShell / FinishedFilm / fade·rise，并明确共享层允许的演进方式（新增可选参数、保持向后兼容）。
P2W8 · 重复度检查停留在手工清单
现象

SKILL.md 要求"渲染前做一次 repeated-string scan"。实际执行方式是测试里手写的 once 数组——每部片只列几个词。以黄耆片为例，once 只写了 ["生山谷"]，而该片里 上经 出现了 4 次、《神农本草经》· 卷一 · 上经 出现了 2 次，都没被捕获。

我按规则做了一次自动扫描，55 部中只有 1 部被标出（人参片的"别名""生境"重复），说明规则和检查是两套东西。

建议
  • 把 repeated-string scan 写成脚本并进测试：抽取每部影片的可见文本节点，自动报告片内重复（允许白名单：署名、免责声明）。
  • 这样 once 手写清单可以退化为补充，而不是唯一防线。

PART 2产品诊断

P0P1 · 可读性承诺与实际产品相反：今译正文只有 42px
现象

SKILL.md 明确规定："Chinese body or quotations should usually be at least 56px，secondary Chinese at least 34px"。实测 51 部可测影片的今译正文字号全部是 40px 或 42px，无一达到 56px；次级说明文字普遍 26–28px，也低于 34px 的下限。

更值得注意的是结构倒挂：以黄耆片为例，古文原文用 72px，而把它翻译成现代汉语的今译只有 42px。也就是说，最需要观众看懂的、降低理解门槛的那一层，是全片最小的字。

影响

这是短视频，没有旁白，观众不会暂停。42px 在 1080 宽的画布上约占 3.9% 宽度，换算到手机屏幕上大约 15pt——低于舒适阅读阈值。再叠加"逐句照译"带来的长句（今译段落常达 50–70 字），实际观看体验是"来不及读完就切场景了"。

这个问题 100% 存在、且没有任何测试或校验在管——它是"规范写得好、执行靠人"这一结构性缺陷在产品侧最直接的后果。

建议
  • 二选一，不能既要又要：要么把今译拆到两个场景（把长句按语义分屏），要么提高字号并精简译文。前者更符合 SKILL.md 已有的"拆分长条目"指引。
  • 把字号下限写进测试（对今译块断言 fontSize ≥ 56），否则规范会继续被无视。
  • 为"注释"块单独定字号档位，避免它和正文抢注意力。
P0P2 · 存量合规欠账没有清理路径
现象

44 部影片仍使用旧式 主治 表述，且 55 部全部缺少新规范要求的功效框架与免责注释。测试的处理方式是"豁免名单"（legacyZhuzhiFilms）——这在工程上是对的（不为了存量破坏新规则），但在运营上等于把问题封存起来。

影响

账号正在养号重建期，而这些影片一旦重新发布或仍在平台上，携带的正是触发处罚的表述模式。豁免名单让"欠账"看起来像"已解决"。

建议
  • 把豁免名单改造成可递减的待办清单：每整改一部就从名单移除一部，测试断言名单长度只减不增。
  • 整改按"是否已发布"排序：已在平台上的优先，未发布的可以低成本重制。
  • 整改内容本身是机械的（今译加前缀 + 加注释行），配合 W2 数据化后可以批量完成，无需逐部重写。
P1P3 · 产能模型不可持续：剩余 302 条目 × 手工 303 行
现象

progress.json 记录 356 个条目，已完成 54，剩余 302 个（含 2 个 skipped）。而当前单部影片的边际成本包括：手写约 300 行 TSX、手写测试表格行、手写 DONE 映射、手写上传台账、人工目检 3 张静帧。

影响

按现有流程，产量上限由人工手写量决定，而不是由内容质量决定。更麻烦的是返工成本随存量线性增长：每次平台规则调整，都要面对几十上百个需要手改的文件——这正是 2026-09 合规升级后 0/55 落地率的原因。

建议
  • 先做"降本"再做"提产"：完成 W2（内容数据化）后，单部影片的制作应变成"填一份结构化内容 + 选版式"，而不是写一个组件。
  • 建立内容模板与校验前置：填数据时就跑合规校验（今译框架、黑名单词、必填字段），而不是渲染后才发现。
  • 把"原书顺序"这条内部规则的执行也交给脚本（目前 build-progress.mjs 已做，但 SOURCE/BOOK 是写死的，换书需要改脚本——建议参数化，以支撑 SKILL.md 描述的多书批次流程）。
P1P4 · 发布侧没有台账，母版与发布版本不一致
现象

upload/ 下只有黄芝一份台账（且影片尚未制作），历史 55 部的标题/描述/话题从未建档。同时，工作流规定"上传时用平台曲库替换 BGM"，意味着仓库里的母版 mp4 并不是真正发布出去的那一版——两者音频不同，且替换参数没有任何记录。

影响
  • 面对平台审核或申诉时无法自证：不清楚线上到底是哪一版、配的什么乐、文案怎么写的。事故记录里"申诉用掉唯一一次机会、材料不齐被驳回"就是这个后果。
  • 母版不可复现：拿仓库文件重新渲染，得不到与线上一致的成品。
建议
  • 强制台账：为 src/finished/ 中每部影片要求一个 upload/<kebab>.md，并加测试断言"每部影片都有台账文件"。
  • 台账增加字段：发布平台、发布日期、发布状态（线上/私密/已删）、平台 BGM 名称、文案快照。历史 55 部至少补齐状态，避免再次"无据可查"。
  • 把"平台替换的 BGM 名称"记入台账后，母版的复现路径就完整了。
  • 注意：仓库内两首 BGM 来自网络音乐站点（爱给网 / 轻音乐网），授权状态未在仓库中记录。既然最终以平台曲库替换，建议在 public/music/ 补一份来源与授权说明，或明确标注"仅作母版占位、不作为发布音轨"。
P2P5 · 内容形态单一，方剂线零产出
现象

SKILL.md 定义了两种模式（single-herb 用"药"印、formula 用"方"印），但 55 部影片全部是单味药，测试也只断言 <Seal text="药"。所有影片固定 360 帧（12 秒）、固定 3 个场景、固定两处切换点。

另外，SKILL.md 写的是"aim for about 12 seconds"（目标约 12 秒），而测试把 durationInFrames={360} 变成了硬性要求——规范留了弹性，测试把它焊死了。

影响
  • 356 部结构完全一致的影片，对平台而言是明显的同质化内容，与账号正在经历的推荐受限处境叠加风险。
  • 方剂是内容差异化最自然的抓手（配伍、君臣佐使、方名故事），但这条线在代码与测试层面完全没有验证过。
  • 12 秒是硬约束时，内容量大的条目（原文长、别名多）只能靠压缩字号解决——这正好是 P1 的成因。
建议
  • 放开时长：把 360 从"硬性断言"降级为"默认值"，允许 360/450/540（12/15/18 秒）并让测试校验"时长与内容量匹配"。
  • 准备 3 套版式变体，按内容形态自动选择（单味药·短条目 / 单味药·长条目 / 方剂），避免 356 部一个样子。
  • 启动方剂线：先做 1–2 部跑通 formula 模式与"方"印，并把测试从"只认药印"改为"按模式认印"。
  • 为"历史语境"设一个固定版位（对应新规范的注释块），让它成为结构的一部分，而不是临时塞进去的一行小字。

PLAN原始建议的整改顺序

以下是首次诊断时提出的方案，供对照；实际执行状态见文首的「整改状态」。

第一步 · 立刻止血：备份 + 存量合规
  • git add -A 纳入全部影片、图片、音乐、测试、脚本、台账，首次提交；配置私有 remote 并 push；母版 mp4 单独备份。
  • 制作黄芝作为"新规范样板片"，跑通 古籍称其主…… + 注释行的完整口径。
  • 把合规校验写成针对影片的测试（而非针对 SKILL.md），先把样板片纳入，再逐部推进 44 部整改。
  • 补建上传台账，至少为 55 部历史影片记录发布状态。
第二步 · 本阶段降本：内容数据化 + 字号刻度
  • 抽 <EntryFilm data={...} layout="A|B|C" />，把影片从 300 行降到 20 行，内容迁到结构化数据文件。
  • 建立 8 级字号刻度与布局栅格，把 46 种字号与手写 top 坐标收敛进版式常量。
  • 把今译正文提到 ≥56px，长条目改为分屏呈现（同时解决 P1 与 P5）。
  • 用数据文件作为唯一事实来源，让 progress.json 与测试表格自动派生，删掉 DONE 手工映射与命名启发式。
第三步 · 随后加固：闸门与清理
  • 自动化重复文本扫描、自动重叠检测（基于布局常量算包围盒）、静帧抽样加密到每 15 帧一张。
  • 去掉测试中的魔法数字计数，改为派生式断言。
  • 接入 CI：npm test + npm run lint + Composition 注册同步校验。
  • 归档三个未被引用的模板与 RootIllustration，并重写 SKILL.md 的"模板隔离"条款指向真正的共享层。
  • 参数化 build-progress.mjs 的书名/来源路径，为切换到下一部古籍做准备。

APPENDIX值得肯定的部分

这份诊断偏严格，但这个项目的工程底子在同类个人创作里属于上游，有几处设计应当保留并作为整改的基础：

  • 规范本身质量很高。SKILL.md 把模式与印章、今译与注释的边界、内容去重、发布话术、验证顺序都写清楚了，"翻译不是评论"这类区分相当专业。
  • 共享壳层抽象是对的。FinishedFilm 统一了音乐淡入淡出与三场景切换，SceneShell 保持 durationInFrames 可选以向后兼容，fade/rise 收敛了动效——这是正确的方向，只是还没走到底。
  • 测试与规则同址、以影片为单位建表，让"新增影片前先写失败测试"这条纪律真的可执行。
  • 授权与署名做到了可验证：credits.json + 测试强制"每张图必须有作者与许可，且片上必须显示"，并检测孤儿条目——这一点比多数自媒体团队严谨得多。
  • 事故记录留档并提炼了教训（不批量删除、申诉前备齐材料），这是可持续运营的关键习惯。
核查方式：直接读取 remotion-video/ 下的 src/finished/（55 部）、tests/、scripts/、progress.json、public/images/credits.json、upload/，并对源码做脚本化统计（布局几何签名、字号分布、合规短语覆盖率、重复文本扫描、git 跟踪范围）。所有数字均为实测值，可用同样方式复现。
