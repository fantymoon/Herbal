### 修复：SRT 时间戳取错（严重）

`scripts/topic-voice.ts` 的 `lastTime` 正则 `/(\d\d):(\d\d):(\d\d),(\d\d\d)\s*-->/g`
匹配的是 `-->` **前面**那个时间（一句的开始），不是结束时间。于是每段时长都被算短了
最后一句的长度：

| 段 | 音频实际 | 算出来 | 被切掉 |
| --- | --- | --- | --- |
| seg-01 | 28.85s | 21.24s | 7.6s |
| seg-03 | 17.66s | 8.91s | 8.7s |
| seg-08 | 25.37s | 18.18s | 7.2s |

成片里就是"话说一半突然断"。**修复后**：总长 266.6s → **348.1s（5.8 分钟）**，
语速从 4.8–9.4（抖动）回到 **4.1–5.1（均匀）**——原来那些"快读"是算错的产物。

**教训**：SRT 每行有两个时间戳，取错一个不会报错，只会安静地切掉内容。
改完必须用 `ffprobe` 抽查一两段 mp3 的实际时长对一下。

### BookPlate 组件（`src/topic-graphics.tsx`）

`Plate` 按 `segment.plate.file` 分派：有书影上 `BookPlate`，否则上 `EraTimeline`。

- `crop` / `box` **都是原图像素坐标**，不是屏幕坐标
- 换算：`屏幕偏移 = (原图坐标 − crop 原点) × (显示宽 / crop 宽)`
- 书影 `crop = {x:520, y:150, w:940, h:620}`（裁右半页）
- **古籍竖排，引文是一整列，所以高亮框窄而高**：`box = {x:962, y:374, w:74, h:168}`
  ——第一版按横框（790×76）写，框到的是标题而不是引文
- 定位只能"渲染静帧 → 看图 → 反推坐标"，两轮对准；想一次算准不可能，
  因为原图里的行距看不出来

**这条经验已写进 skill**：书影是"证据"那一半，信息图是"结构"那一半，缺一不可。

### 高亮框定位：踩了三个坑才对

用户第一眼就看出来了：**「好像框住了个空白」**。确实——框落在空白列上。

**坑 1：在整页缩略图上目测坐标。** 列与列只隔约 80px，缩略图上根本分不出来。
两次目测，一次偏左一列、一次偏左两列。

**坑 2：`<Img>` 直接设 width/height + 负偏移不生效。** Remotion 的 Img 不会那样铺开，
书影只渲染出左侧一条，于是"框在书影外面"——这个现象让我误判成坐标错，又去调坐标。

**坑 3：古籍是竖排，引文是一整列。** 第一版按横框（790×76）写，框到的是标题。

**可靠做法**：把目标区域裁成窄带、放大 2 倍、叠 40px 一格的标尺再读。
最终值 `box = {x:1315, y:298, w:92, h:428}`（9 个字的一列）。

```bash
python -c "
from PIL import Image, ImageDraw
im = Image.open('public/plates/yinshan-p06.jpg').convert('RGB')
X0,Y0,X1,Y1 = 1120,240,1460,720
c = im.crop((X0,Y0,X1,Y1)); d = ImageDraw.Draw(c)
for x in range(X0,X1,40):
    d.line([(x-X0,0),(x-X0,c.height)], fill=(255,0,0), width=1)
    d.text((x-X0+2,2), str(x), fill=(255,0,0))
c.resize((c.width*2,c.height*2)).save('.workbuddy-ai/tmp/narrow.png')
"
```

**修复后的 BookPlate 写法**：外层 div 定尺寸、`overflow:hidden`，内层再套一层显式尺寸的
div 承载 `<Img>`（`width/height:100%`），`left/top` 用 `-crop.x*scale` / `-crop.y*scale`。

**教训**：定位图像里的元素时，"渲染 → 看图 → 反推"这条环路太慢也太不准；
**先在原图上量准，再改代码**。PIL 就在手边（managed venv 里有 12.3.0），没有理由靠猜。

## 新片：肉松蓉（第二条短形态）

- 360 帧 / 12.05s / 2.2MB，3 屏各 4 秒，古典屏 13.5 字/秒。
- 钩子「名字的意思是「从容」」——**刻意避开功效方向**。这一条的经文有「强阴，益精气，多子」，
  是容易被平台盯上的那类内容；钩子取名字义，出处是《本草纲目》「此物补而不峻，故有从容之号。
  从容，和缓之貌」。孙星衍案「蓉，即是容字，俗写苁蓉，非正字也」——**底本作「肉松蓉」，
  今通行的「肉苁蓉」是俗写**，这一层进了注释，facts 里用「今名 肉苁蓉」搭桥。
- 配图 `rousongrong-cistanche.jpg`（CISTANCHE DESERTICOLA / DUNCAN BROOKS / CC BY）。
  **物种正确的只有 14 张，多数是干枯果穗**（不好看）；属内（`Cistanche`）有更漂亮的开花照但物种对不上。
  最后在物种正确的那批里找到一张开花的（149062835），用它。**先按物种筛，再在物种内挑好看的。**

## 三个坑，都修了

### 1. 短形态的字号写死 1.6 倍，长原文会溢出

本经原文从 30 到 130 字不等，写死的字号对短的刚好、对长的会撞底。改成**阶梯自适应**：
从 1.6 往下试到 1.0，取第一个装得下的（`room = CANVAS.height - BOTTOM_RESERVE - CLASSICAL_TOP`）。
肉松蓉落在 109px / 预留 1031px。

### 2. 脚手架写的草稿文案被永久冻住（真 bug，影响每一部片）

`new-film` 在建片时就把 `draftTitle`/`draftDescription` 写进台账，而 `renderLedger` 的
`keep()` 是**只填空不覆盖**——于是文案在"内容还没写"的那一刻就被定死了，之后 `npm run ledger`
再也刷不动它。蒺藜子那次我手动改的，这次发现了根因。

修法：`renderLedger` 加 `blankCopy` 参数，`new-film` 传 `true`，**脚手架写台账时把
标题/描述/话题留空**，等内容模块写完后第一次 `npm run ledger` 再填。

### 3. `tests/finished-video.test.ts` 的 TDZ 缺陷（我加片触发的）

`const renderableFiles` 定义在第 382 行，却被第 259 行的测试使用。中间隔着**顶层 `await`**
（逐片 `loadContent`），而 node:test 在顶层 await 挂起期间就开始跑已注册的测试了。
片数少时 await 恰好先完成，看不出问题；加到第 69 部就稳定报
`Cannot access 'renderableFiles' before initialization`。

修法：把那段异步加载**整体提到所有 `test(...)` 注册之前**，并写明为什么必须放在那儿。

**lint 仍有一条红，属于另一条线**：`src/topic-film.tsx:4 'EraTimeline' is defined but never used`。

## 续：BGM 该不该扩库（以及扩库之前先撞见的事）

用户问「应该再找一些 BGM 进行轮换，你觉得如何」。查下去先撞见一个真缺陷。

### 六分钟母版的音床在 4:16 就没了

`out/tu-que-h.mp4` 6:01.75，配 `yuzhou-changwan.mp3`（4:16），`<Audio>` 没有 `loop`。
**ffprobe 全过**——它报的是健康的 AAC 流。缺陷在采样里：按 0.5 秒窗口量，4:16 之前最安静的
窗口是 -50 dBFS，4:16 之后出现 **11 个 -180 dBFS 的窗口**，那是真的零。口播盖住了大部分，
句子之间的空隙才露出来。

修的过程有个坑值得单独记：`@remotion/media` 的 `loop` **从 `trimAfter` 推循环长度**，取不到
资源时长时把媒体当无限长。于是「`loop` + 整片长度的 `trimAfter`」= 只播一遍，无报错、无警告。
第一次改完重渲，新旧音轨**逐位相同**——**改完要量，不能只看代码对不对**。把 `trimAfter` 换成
曲子自身长度（7678 帧）后，同两个窗口从 -180 变成 -37.9 / -38.6。

曲子开头自带 0.96 秒静音，循环时每个接缝会多一个空洞，所以注册表同时记 `leadFrames`，
`trimBefore` 用它。修完的母版全片只有一处 0.11 秒静音（开头淡入），接缝处无空洞。

### 曲长不能靠猜，也不该硬编码

`sync-music` 现在写 `src/music-registry.ts`：曲长、开头静音、来源。曲长用**纯 JS 走 mp3 帧头**
数出来（与 ffprobe 差 0.026 秒，一帧之内）。**更正一条旧记录**：不是「沙箱禁止 Node spawn」——
被拒的是**同步**形式（`execFileSync`/`spawnSync` 返回 EBUSY），异步 `spawn` 完全可用，
`verify-film.mjs` 早就把这条写在注释里了。第一次写音床检查时用了同步形式，解码静默失败、

  若没做，扩库才直接影响观感。**两种情况下的投入建议相反**，所以这是最该先问用户的一句。

### 对「扩库」的判断：四层里最浅的一层

给用户的答复框架——**先别扩库**，理由是这件事有四层，扩库在最外层：

1. **运营层**（上传时换平台配乐）：零代码，效果最大，前提待用户证实。
2. **分配层**（哪部用哪首）：**已解决**，发布顺序完美交替，今晚固化成了门禁。
3. **库容层**（再找曲子）：**已探明**，可达的授权源只剩 FMA 一家且无接口。
4. **身份层**（固定开场/收尾音、口播）：**真正的杠杆，完全没用过**。同样两首曲子配一个固定开场，
   辨识度提升远大于五首曲子随机分配。

**判据：一个「再找几首」的诉求，先问它落在哪一层。** 分配层的缺陷有门禁能查；库容层的缺陷
（说不出授权）也能量；运营层和身份层的缺陷没有任何自动化能看见——**它们恰好是这两层一直没动的原因。**

## 配图的三次取舍（都记下来）

1. **蒲黄**：香蒲（T. orientalis）的可用照片里**没有一张拍清穗子**，全是叶片和生境。
   最后用了属内的杂交香蒲（`TYPHA × GLAUCA`），因为它**正好拍到上下两段穗**——
   上面那段就是出蒲黄的地方，正对案语「中出黄」。署名如实写属与种，内容模块与描述里都点明。

2. **香蒲**：用香蒲本种（`TYPHA ORIENTALIS` / WILLIAM HARLAND / CC BY）。
