长期事实与约定。项目内的权威文档是 `AGENTS.md`（工程约定）与 `.agents/skills/herbal-short-video-production/SKILL.md`（制作规范）；这里只记它们没写、但每次工作都需要知道的东西。

## 账号处境

- 视频号因"尚未被现代科学证实或夸大功效"被减少推荐，**生效在 2026-08-19 与 08-21 之间**
  （平台导出回填：08-19 菟丝子 1642 播放 → 08-21 起 0–29，且完播率同期未变差）。申诉机会
  已用完；客服工单待发。详见 `remotion-video/upload/_incidents.md`。
- 定位已转为**文化 / 读书**向：分类选文化读书，简介如"每日读一段本草古籍"，不出现养生、调理、健康科普字样。
  **已机器强制**：`OFF_POSITION_WORDS`（`养生`/`调理`/`健康科普`/`疗效`/`药效`/`治病`/`防病`）出现在
  标题/描述/话题即 FAIL；话题默认值也改成 `#<书名> #本草 #古籍 #传统文化 #读书`（原 `#中草药` 招来的
  正是降权针对的人群）。
- **平台处罚落在文案上，不落在画面上**——所以门禁扫的不止是片内文字，还包括台账的
  `标题：`/`描述：`/`话题：`（`checkLedgerCopy`，与片内共用同一张违禁词表）。只扫画面会放出一部
  画面合规、标题不合规的片。**一个与既定定位相矛盾的生成器默认值，是留给下一部片的陷阱。**
- **标题框架是集合性质，单部片查不出来**：SKILL.md 禁止跨片复用同一提问模板，`checkTitleFrames`
  把药名与「」里的词当槽位剥掉后比框架，两部相同即 FAIL。只有 `check-films.ts` 能查（它看得见全集），
  `verify-film.mjs` 只看得见一部片，接不上。**这类「集合性质的不变量」是新的门禁品类。**
- 抖音无警告，是基本盘。
- 55 部母版（`out/` + `src/finished/`）完好，仅平台副本曾被删。
- **在线的不止那 55 部。** 09-27～10-01 又发了 5 部：黄芝、蓝实、紫芝、防风、决明子。
  `frozen-films.ts` 是 2026-09-21 的快照（老片没有台账可读，快照是唯一办法），所以这 5 部不在名单里；
  现在 `npm run check` 从台账读 `已发布 <日期>`（`publishedOn`）补上这一判断，读到的按冻结片同等待遇
  ——**一部在线片撤不回来，判决没有意义**。空字段不算日期，所以漏记反而更严。
  `npm run check` 现在的输出：`N renderable, 0 draft, 55 frozen, M published`。
  **判据：写新规则前先问「它会不会判一部在线片 FAIL」**——会，就得先决定这部片是否豁免。

## 内容硬约束

- **功效句必须框定为历史认知**：`今译` 里的功效句以 `古籍称其主……` 开头，`注释` 块必须含 `此为汉代认知，未经现代科学证实`。
- 被禁现代疗效动词（片内今译/注释、标题、描述、话题）：`治疗`、`主治`、`改善`、`有效`、`根治`、`特效`、`治愈`、`秘方`、`神效`、`必备`、`包治`、`断根`、`奇效`、`立竿见影`、`药到病除`。
- `今译` 是逐句现代汉语翻译，不是概括评论；评论/说明一律放 `注释` 块。
- **一个词的读法要找对「对本条作证」的那条证据，后世语料不能替本条作证。** 龙眼「安志厌食」的
  「厌」读平声、义为**饱足**：《本草经解》附余·考证·龙眼对**这一条**给了直接训释（「厌平声。饱也。
  纲目称其开胃益脾。补虚长智。即安志厌食之谓也」）。我曾按「全库 79 处『厌食』都作『恶心厌食』」
  写成「不欲饮食」，那 79 处全是后世用法。**手边有一个大规模、好检索、方向一致的证据，恰恰是绕过
  那条唯一直接证据的最舒服的方式。** `--grep` 的命中数不是权威性。
- **`今译` 与 `注释` 不得给出互相矛盾的训释。** 两处对同一个词各说一套，比任一处写错都更难被发现，
  而且没有门禁会替你看这一眼（龙眼曾同时出现「安于饮食」与「指不欲饮食」）。渲染前逐条核对。
- 三屏（hero / classical / closing）是既有视觉语言；时长档位见 `ALLOWED_DURATIONS = [360, 450, 540, 630, 720]`，**实际只会落到 450/540/630/720（15–24 秒）**——360 已不可达（每场景至少 120 帧 × 3 屏 + 阅读预算）。`EXTENDED_DURATIONS = [810, 900]`（27/30 秒）**只能靠声明 `duration` 偏离到达**。
- **容量上限：今译×1.55 时，标准档 83 字原文；声明 `duration` 后 130 字**（×1.8 → 83/112；×2.1 → 66/102）。
  这是拿真 `planFilm` 扫出来的，不是估算：古典屏同屏装原文+今译+注释+历史框定，**原文长度才是约束**。
  84–130 字这一段正是 `deviations` 解锁的区间。旧记录写的「78 字」偏保守，已更正。
  实测方式：固定原文长度、令今译 = 原文 × 比例，扫到 `findReadingProblems`/`findOverflow` 首次触发。
- **屏幕上的事实只有 `产地` 是凭记忆写的，所以它现在是门禁。** `别名` 从经文的 `一名…` 句读出来，
  `篇目位置` 从 `<目录>` 读出来，`产地` 脚手架从来不派生——大枣因此在结尾屏写「池泽」，而经文写「生平泽」，
  「池泽」是紧邻的藕实茎的生境。`originProblems`（`corpus.ts`）要求 `产地` 是经文点名的地名；
  脚手架改用 `originOf(sutra)` 从经文末的 `生X` 派生（278/350 条有条目名，其余本经不记生境，可由别录补）。
  **已知同病且在线、不能改的三部**：蓝实（河内／经文作 生平泽）、紫芝（高夏／生山谷）、黄芝（嵩山／本经无生境），
  在 `tests/corpus.test.ts` 里钉住，只减不增。
- **`deviations` 是「预算可谈、安全不可谈」的分界**（`src/layout.ts` 的 `NEGOTIABLE_RULES`）。
  安全规则（违禁词、历史框定、免责声明、几何、配图）**没有豁免通道**——「能渲染的必然合规」靠的就是这条。
  预算规则（`duration` / `reading-budget` / `pacing`）可凭**非空理由**豁免，豁免不删除违规，只盖 `waived` 戳，
  `npm run check` 会把影片自己的理由打印出来。空理由、或点名安全规则，都判 `deviation` FAIL。

## 协作方式

- **这个工作流由大模型驱动，不要为「判断类」的事写生成器。** 标题、描述这类文案，模型自己
  写就行——`draftTitle` 只是保证字段非空的占位，不是作者。我曾把「别等我敲定」读成「去写个
  更好的生成器」，加了一堆候选拼装逻辑，被否掉。**判据：需要品味的地方用判断，需要重复的
  地方才用代码。**
- **能自己产出的就别问。** 用户明确说过「这些应该在工作流里批量生成的东西你就别等我敲定」。
  只有当决定依赖只有他知道的信息（平台后台、他的偏好）时才问。

## 生产约定（重构后）

- 新片是**数据不是 JSX**：`npm run new-film -- --id=<CompId> [--latin=] [--entry=]` 一次生成内容模块、影片包装、上传台账三件套。
- 默认取 `progress.json` 首个 todo（原序），但 `--entry=` 可跳选——**生产顺序与发布顺序是两件事**，SKILL.md 明确禁止在片内展示工作流顺序。发布顺序见根目录 `publish-plan.md`。
- 内容模块留 TODO 即为 draft：`gen` 不注册、`verify` 拒绝渲染，所以 draft 无法上线。
- 不要手写 `position: absolute` 或自选字号，全部走 `src/layout.ts` 的 `TYPE`；否则门禁 FAIL。
- 55 部已发布影片在 `scripts/lib/frozen-films.ts` 里冻结，只减不增。**已发布的条目不再重做上线**；要重制必须先下架旧片再替换。
- **两个预算都要过门禁**：几何（不重叠、不溢出、每屏 ≥120 帧）与阅读（`READING_RATE_LIMIT = 15` 字/秒，`reading-budget` 规则）。时长由每屏阅读量决定，档位 450/540/630/720；360 已不可达。
- **台账不要手写**：文案字段由 `ledger` 生成，数据列由 `stats` 从平台导出并进（见下「工具」）。
- **语料是 GB18030，不是 UTF-8——`rg` 在整条语料线上完全失效**。701 个 txt 全部如此，UTF-8 字节匹配
  零命中，会把「明明有这一条」报成「查无此条」。检索一律用 `npm run entry -- --grep=<词>`（先解码再搜），
  核对单条用 `--name=<条目名>`。`AGENTS.md` / `SKILL.md` / `publish-plan.md` 里的 `rg` 指引已改。
- **语料里的条目名有残缺**：`000-神农本草经.txt` 中至少 17 条 `<篇名>` 被截断（如 `青`→青蘘、`木`→檗木、`KT`→编码残缺）。开新片前必须核对内容行首句，把全名写进内容模块的 `entry`。
- **语料残缺有三类，前两类看得见，第三类看不见。`npm run entry` 只拦前两类**（350 条里 3 条截断 + 28 条掉字）：
  ① **经文断在连接词上**（卷柏「…轻身、和《吴普》曰」）；② **行内掉字**——底本用空格占位，
  如龙骨「惊痫 疾狂走」、黄连「目痛、 伤泣出」。**空格归一化会把缺字悄悄粘成通顺句子**，比明显空缺更危险。
  遇到就跳过或换底本，不要猜字（「原文照录」没有改字的余地）；确要补字就用
  `new-film --recension=<字> --why=<据何本>`（两者必须同时给），补字与依据会写进内容模块注释和台账备注。
  ③ **讹字**——字写错了，读起来是通顺的汉语、行内没有空格，所以 `corpus.ts` 抓不到。大枣底本作
  「肋十二经」、证类本草作「助十二经」，在那儿躺了很久才被看见。**开新片前跑 `npm run variants`**。
- **`npm run variants` 是报告不是门禁**（`scripts/variants.ts`）：底本与《证类本草》逐条 LCS 对读，
  645 处单字差异，按「只有一侧得到全库作证」筛出 24 处。**判据要两半**——两侧不同 × 底本那一读法
  全库几乎无人作证；只取一半都不行（「凡差异皆错」报 174 处，「底本独有的字串」报 291/377，独特 ≠ 错）。
  24 处里仍有半数古今字（创/疮、利/痢、注/疰），**把它们也筛掉就等于把「我已经相信的东西」编进筛子**，
  所以分类留给眼睛。采他本读法必须在 `注释` 里写明版本异文（大枣的注释就是这么写的）。
- **语料读取统一走 `scripts/lib/corpus.ts`**（`findEntries` / `sutraOf` / `defectOf` / `originOf` / `originProblems` / `fillGaps`），`new-film` 与 `entry` 共用。
  以前两处各写一份，`new-film` 只读 `内容：` 的**第一行**，于是所有跨行经文都被生成成截断的 `original`
  （决明子曾被生成成「…益精光（《太平御览》」——读起来像完整句子）。新片先看 `original` 有没有断在半句。

## 配图通道（2026-09-27 打通）

- **维基媒体与 Openverse 在这台机器上不可达**（本机走代理出网；`upload.wikimedia.org`、`commons.wikimedia.org`、
  `api.openverse.org`、`wsrv.nl`、`cdn.statically.io`、`archive.org`、`pixabay`、`gitee` 全部超时/403）。
  SKILL.md 写的两个图源通道在这里都用不了——**但 SKILL.md 第 33 行已经写了备用通道，照它做就行**。
- **可用通道是 iNaturalist**：`api.inaturalist.org`（查询，带许可与署名）+ `inaturalist-open-data.s3.amazonaws.com`（图片）。
  只取 CC0 / CC BY / CC BY-SA（-NC/-ND 不可用于商用平台）。用 `npm run fetch-photo` 一条命令完成查询+下载+登记。
- **三个坑**：
  ① **扩展名因图而异，不是固定的**。桶里有的图是 `large.jpg`，有的是 `large.jpeg`——同桶、同许可都可能不同
  （166792593 是 `.jpeg`，585667156 是 `.jpg`）。**旧记录写「一律用 `.jpeg`」是错的**，硬编码任一种都会
  静默砍掉一半图库：整个分类看上去「没有可下载的图」，其实有一百张。脚本现在从 API 返回的 `photo.url` 读扩展名，另一种做兜底。
  ② **不是每张 CC 图都在开放数据桶里**，有些 id 返回 404，要按候选逐个试。
  ③ 代理会偶发 `ECONNRESET`，脚本已加 3 次退避重试（`--retries=`）——没有重试时，一次抖动会被报成「这个分类没有图」。
- **`--id=<photoId>` 按 id 取图**：自动排序只是启发式（横向 → 分辨率 → 许可），看不出「密叶丛」比「整株带花」差，
  所以先 `--check` 列候选、肉眼看、再按 id 取是正常流程。`--file=` 是**文件名主干**，传了 `.jpg` 也不会变成 `.jpg.jpg`。
  横向原图的 `large` 档就是 1024px ≥ 932px 插框，体积只有 `original` 的 1/4；竖图会自动降到 `original`。
  插框是 `objectFit: cover` + `objectPosition: 50% 50%` 的横向裁切（约 1.9:1），**竖构图会切掉主体**，优先挑横向图。
- **`--fruiting` 是「画面里有没有果实」的唯一可用信号**（iNaturalist 物候标注 `term_id=12&term_value_id=14`）。
  自动排序看不见内容：龙眼可用 96 张里前 10 张全是叶子，加 `--fruiting` 后 16 个观察、64 张可用，一眼挑到结果的树。
  大枣也借它从青果换成满树红枣。`--list=N` 让候选列表不再限于 10 条。
  **注意 `--id=` 查的是未过滤列表**，要 `--fruiting --id=` 一起给，否则报「no candidate with photo id」。
  果部条目优先用这个开关——「配图为<X>」写在台账描述里，青果/叶子与条目名对不上就是内容错误。
- **Node 走代理**：`fetch` 默认不读 `http_proxy`，脚本里设 `process.env.NODE_USE_ENV_PROXY = "1"` 即可（Node 22 就支持）。
  **子进程：异步 `spawn` 可用，同步形式（`execFileSync`/`spawnSync`）会返回 EBUSY。** 旧记录写的
  「沙箱禁止 Node spawn 子进程」是错的——`verify-film.mjs` 早就在 `run` 的注释里写了这条。用同步形式
  写音床检查时，ffmpeg 解码静默失败，表现成「这个文件没有音频」，是个会把人带偏的假象。
  所以下载类脚本仍留在 Node 内（不为沙箱，是为了重试与代理），但需要 ffmpeg 时可以 spawn 它。
- 其他可达的图源（备用）：`plants.sc.egov.usda.gov`（USDA PLANTS，公有领域）、`calphotos.berkeley.edu`（伯克利，CC 带署名）、
  `api.gbif.org`（聚合，但媒体直链常指向被封的 CDN）、`raw.githubusercontent.com`。
- 台账约束不变：`credits.json` 必须与 `public/images/` **完全一致**，且**每张图都要被某部成片引用**——
  下载与建片必须成对，不能先囤图。

## 音乐通道（2026-10-05）

- **曲长是门禁的输入，不是注释。** `npm run sync-music` 复制曲目并写 `src/music-registry.ts`：
  曲长（纯 JS 走 mp3 帧头数出来）、开头静音、来源。片子写的曲子不在表里，`npm run check` FAIL。
- **`@remotion/media` 的 `loop` 会静默失效。** 它从 `trimAfter` 推循环长度；取不到资源时长时把媒体当
  无限长，于是「`loop` + 整片长度的 `trimAfter`」= 只播一遍。没有报错、没有警告，只是音床在曲子
  放完处停了。`FinishedMusic` 因此查注册表，把 `trimAfter` 设成曲子自身长度。
  **判据：库的「聪明默认」在取不到输入时会退化成无操作，而退化路径不报警。**
- **`trimBefore` 用曲子的开头静音长度**，否则每个循环接缝会多一个 0.96+0.55 秒的空洞。
- **`ffprobe` 通过不代表音轨没问题**：它报的是流，不是采样。`verify` 与 `topic:verify` 都会解码
  音轨，断言曲子起播后没有 ≥1 秒纯零段（判据是 `-180 dBFS` 这种只有「什么都没有」才到得了的地板）。
- **长视频系列此前完全没有检查**，缺陷正活在那里。`npm run topic:verify [--verbose]` 补上了。
- **发布顺序 ≠ 书内原序。** 按 `progress.json` 原序量 BGM 轮换，14 部新片相邻同曲 8 处；按
  `publish-plan.md` 的发布顺序量，前六部完美交替。**数字没错，是序列错了。** 现在
  `adjacentTrackRepeats` 从 `publish-plan.md` 解析排期表做这条检查，解析不出 30 行就 FAIL。
- **音乐来源在这台机器上只剩一家**（2026-10-05 实测）：Free Music Archive 200 但无可用接口
  （检索页前端渲染，`/api/*` 全 404）；incompetech 200（CC-BY，西方合成器风格，声纹不搭）；
  musopen 403；**爱给网 403**（更正：此前记的「可达」是偶发）；archive.org / Commons /
  Openverse / Pixabay 全超时。**「找不到更多曲子」是可达性事实，不是没找。**
- **全库分布：72 部片 77 处引用，53 处渔舟 + 24 处高山（69% / 31%）。** 但每部片只用 12–30 秒，
  两首曲子是 4:16 与 3:33——**素材量不缺，缺的是「不同的曲子」**，所以问题不在库容。
- **「再找几首 BGM」是四层里最浅的一层**，判据：① 运营层（上传时换平台配乐，零代码、前提待证）
  ② 分配层（哪部用哪首，**已解决**并有门禁）③ 库容层（**已探明**，只剩一家源且授权说不清）
  ④ 身份层（固定开场/收尾音、口播，**真正的杠杆，完全没用过**）。**同样两首曲子配一个固定开场，

## 工具（都别手写产物）

- `npm run ledger` 生成台账文案字段（只填空不覆盖）；`npm run stats -- --file=<导出>` 把抖音/视频号导出并进台账（两平台列名与数字格式都已归一化，按「日期+平台」去重）；`npm run audit -- --markdown` 重出处置清单。
- `npm run entry -- --name=<条目>` 读经文、算容量、查残缺（截断 + 掉字）；`--list [--fits]` 列出全部条目；`--grep=<词>` 跨 701 个语料文件检索（唯一能搜中文的通道）。
- `npm run variants [-- --all]` 底本与《证类本草》对读，报讹字候选（报告，不判失败）。
- `npm run fetch-photo -- --taxon="<学名>" --file=<主干> [--check] [--list=N] [--fruiting] [--id=<photoId> | --pick=N]` 取真实授权配图并登记。
- `npm run sync-music` 复制曲目并重写 `src/music-registry.ts`（曲长、开头静音、来源）。**加曲目：把 mp3 丢进 `music/`，在 `scripts/sync-music.mjs` 的 `TRACKS` 加一条，再跑它。**
- `npm run new-film` 建片，`npm run gen` 注册，`npm run check` 全量门禁，`npm run verify` 单部渲染验证（含音床检查），`npm run topic:verify [--verbose]` 检查长视频系列（含音床与静音时刻）。
- 过拟合审计见工作区根目录 `overfit-audit.html`：A 项（历史框定句）已定并实施，余 B/C/D/E/F 五项已授权由我决定。

优化计划见工作区根目录 `optimization-plan.html`，发布排期见 `publish-plan.md`。
