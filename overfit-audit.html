已修闸门校验了一个对输出毫无影响的字段
现象

compliance.ts 检查 mode 是否属于 single-herb | formula，失败时报 seal: mode "x" has no seal glyph。但渲染器里印章是硬编码的 <Seal text="药" />，layout.ts 完全不读 mode。

于是 mode: "formula" 能过闸门、仍然渲染「药」。规则名字里写着 seal，行为上什么都不保证。这是最坏的一种过拟合：验形状不验行为——模型只要把枚举值打对就能"满足"规则，而片子是错的。

修法

SKILL.md 第 39 行其实早就写明了实现方式（<Seal text={mode === "single-herb" ? "药" : "方"} />），是代码没跟上文档。现在把映射提成布局层的纯函数 SEAL_GLYPH / sealGlyph(mode)，渲染器读它，并加测试断言 sealGlyph("formula") === "方" 且两个 mode 不共用字形。

顺带的好处：加 mode 现在是编译错误而不是静默回退——Record<mode, string> 少一个键就报错。

同时修掉测试里 assert.equal(entryFilm.includes('<Seal text="药"')) 这类硬编码字符串断言——它断言的正是那个 bug，是过拟合的另一面。

已修脚手架声称的流程是假的，新片仍需手改配置表
现象

npm run new-film 打印的第 5 步写着「npm run progress（从内容文件自动拾取）」。实际上 build-progress.mjs 的 done 映射来自 scripts/books/*.mjs 里手写的 { 黄芝: "HuangzhiFirstFilm" }，而它还会反向校验：磁盘上有一部未登记的成片就 exit 1。

也就是说，照脚手架说的做，第 5 步会直接失败；真正的手工步骤（改书配置）根本没被写出来。数据化承诺的"五处手工维护收成一处"当时只兑现了四处。

修法

数据化影片的内容模块本来就同时带着 entry 和 id，所以 build-progress.mjs 改为从内容模块派生映射，手写表退化成「55 部手写老片的遗留补充」，且冲突时以内容模块为准。

实测验证：把黄芝从手写表里摘掉后重跑，progress.json 逐字节不变，仍报 55/356 done、下一部紫芝。新片从此不需要改书配置。

A历史框定句要求逐字相等，而规范自己说的是「诸如」
证据

compliance.ts:93 原是 content.historicalNote !== REQUIRED_NOTE（字节相等）。
SKILL.md 第 87 行：「注释 块必须带一行诸如 此为汉代认知，未经现代科学证实」。

问题

代码比规范严，而且严得没有产品理由——它固化的只是当初写下的那一串字。任何更好的措辞（「此为汉代说法，现代科学未予验证」）都会 FAIL，而且改措辞要改代码，规则不可证伪。

决定：② 改成语义检查（已实施）

规则改为 hasHistoricalFrame（src/layout.ts），检查这句话做了三件事，不检查它等于哪串字：

  • 点名时代或古籍出处——汉代 / 古人 / 古代 / 古籍 / 历代 / 旧说 / 本草经 ……
  • 否认现代知识已证实它——否定词须在同一小句内够到「证实 / 验证 / 证明 / 确证 / 确认」。这条带窗口约束：未经现代科学证实 过，未经删改，现代科学证实 不过（否则「未」和「证实」分属两件事，等于没否认）。
  • 点名一个现代知识领域——现代 / 科学 / 医学 / 实验 / 临床 / 药理。单写「未经证实」不够：平台投诉针对的正是现代科学口径的功效主张，这句话要正面回应它。

三个要件各自具名（FRAME_PARTS），所以失败信息会说缺哪一项，而不是只说「不匹配」。REQUIRED_NOTE 保留为推荐措辞，不再是唯一答案。

验收

测试先反向证明能失败：空串 / 无否认 / 无时代 / 无现代领域 / 以及上面那个「假否认」窗口用例，五个都必须 FAIL； 另加一条正向用例证明灵活性真的到手——《神农本草经》所载，现代医学尚未证实、古人旧说，未获现代实验确证 均通过。 157 测试全绿、lint 干净、check 仍 1 renderable + 55 frozen。

零漂移：npm run audit -- --markdown 重跑后 _frozen-disposition.md 逐字节未变，仍是「55 部无历史框定句」。 published-audit.ts 刻意保持严格字面匹配——它问的是事实（那部已发布影片当时有没有那行字），放宽会把从没展示过免责声明的旧片记成「有」。

B没有任何「逐片合理偏离」的表达方式
证据

全仓搜索 override / waiver / exempt，命中的全是硬编码豁免（书名号引用、ASCII 署名下限）。逐片偏离只有两条路：改共享引擎 + 改测试，或者加进 frozen-films.ts（后者被明确禁止）。

问题

这才是真正损失灵活性的地方。冻结清单处理的是过去（55 部不改），对未来的"这一部确实该不一样"没有任何词汇。模型的判断无处安放，于是只剩两种结果：要么被规则挡回去，要么有人偷偷改引擎。

实测：这个需求不是假想的

拿语料里的真实条目跑一遍计划器（planFilm + checkPlan），容量上限取决于全片可读总字数（阅读预算 15 字/秒 × 封顶 24 秒 = 360 字），而今译约为原文的 1.5–2 倍：

今译 / 原文能承载的原文上限说明
× 1.55≈ 78 字黄芝实测比例。它的 33 字已经吃掉 630 / 720 帧，只剩 3 秒余量
× 1.8≈ 66 字长句更啰嗦的正常情形
× 2.1≈ 60 字古病名多、要解释的多

再统计语料：340 条可识别经文里，307 条（90%）在 60 字以内，24 条落在 61–78 字，9 条超过 78 字——包括 丹雄鸡（137 字）、桑根白皮（91）、白马茎（89）、龙骨（88）。

也就是说：这条线现在就在切语料。那 33 条放不下的，只有两条出路——删原文（违反「原文照录」和「今译逐句」），或者全局抬高档位（那会让每一部片子的时长选择都变，不是「这一部特殊」的表达）。没有第三条路说「这一部我知道，它就是要 30 秒，理由写在这儿」。

注意这跟「阅读预算 15 字/秒」不是一回事，那条不该动——它量化的是观众读不读得完，与内容无关。要放宽的是时长档位的上限，而且应该按片放：不是让每部片都变长，是允许长条目那一部有更长的片子。

建议

加 content.deviations?: { rule: string; why: string }[]：闸门把列出的规则降级为 warn，check --verbose 打印理由，并断言偏离必须带非空理由。这样偏离是可见、有成本、留痕的——而不是静默豁免。

C场景语法封闭，内容 schema 装不下项目自己选的方向
证据

ScenePlan.kind 只有 hero | classical | closing，planFilm 是固定三步。18 个内容字段全部贴合「单条目·单味药」。

而 SKILL.md 第 86 行自己写着 注释 该承载「历史背景、版本异文、术语说明、安全框定」四项——schema 里只有一个 commentary: string。黄芝那部现在就把古病名、方术语义、德行言药、产地出处四件事挤在同一个字符串里。

语料里还直接躺着另一种形态：丹雄鸡、白马茎、龙骨、桑根白皮 都是「一条之下并列多个部位，各部位各有主……」，比如丹雄鸡一条里就有头、肪、肠、裹黄皮、尿白、黑雌鸡、翮羽、鸡子、鸡白蠹 九组。现有 schema 的 original: string + translation: string 只能把它们压成一段散文，而逐句今译的要求正是要求把它们分开——两件事直接冲突。

问题

要加一屏「名字由来」或「注家分歧」，必须同时改 layout.ts + entry-film.tsx + TYPE + 测试。也就是说，项目一旦真按名物考据的方向走，每一部新形态都要先做一次引擎改造。这比任何单条规则都更限制灵活性。

建议

给 FilmContent 加 sections?: { kind; label; text }[]，让 planFilm 把它展开成额外的古典屏。这是让"内容数据化"真正兑现的一步。

但要看清 C 不解决什么

C 解决的是形状，不是容量。总容量 = 阅读预算 15 字/秒 × 时长，分屏只是切法——加屏不增加能装多少字。所以 C 做完，丹雄鸡那 137 字照样放不下；而且加屏本身还要时间（每屏 ≥120 帧，第 6 屏至少要把片子推到 840 帧以上，同样撞 B 那面墙）。

这也是我先前把 B、C 并列成"两个杠杆"时不准确的地方：B 才是动容量的那个，C 动的是形状。按语料的紧迫程度，B 更靠前。

D原文不能切分，今译可以
证据

只有 splitTranslation()。content.original 在 layout.ts 里只出现两次，都是整块塞进第一个古典屏。

问题

长条目（下经多长条）的原文只能靠"删到放得下"，而它的今译却能跨三屏。这是历史遗留的不对称，不是规则——没有任何产品理由说原文不该切分。

E重复扫描用「书名号 + 卷篇部」当"引用"的替身
证据

isAllowedRepeat = text.includes("古籍内容展示，不构成诊疗建议") || (text.includes("《") && /[卷篇部]/.test(text))

问题

它编码的是"那 55 部恰好印了什么"，不是"什么算必需署名"。重复出现的摄影师署名、或没有卷次的方剂组成引用会被误判；反过来 《》 包起来的正文会被放过。目前的语料恰好让这个替身够用。

F时长上限 24 秒（这条不是过拟合，但要知道代价）
说明

ALLOWED_DURATIONS = [360, 450, 540, 630, 720]，SKILL.md 与代码完全一致，是有意的产品决定而非漂移——所以我把它列为取舍，不是缺陷。

代价

它同时关掉了"更长、更收藏向"的形态。如果策略往那边走，这个常量必须跟着走；它不会自己放宽。

KEEP没有过拟合、应当保留的部分

避免把好约束一起改松。以下都是刻意的设计，核对后认为站得住：

约束为什么不是过拟合
冻结清单 55 个文件名刻意的棘轮：只减不增，且有测试断言它不腐烂。它管的是过去，不是未来。
禁用疗效词表平台风险，不是对语料的拟合。账号已经因此被限流一次。
免责声明 / 真实授权配图 / 不代码绘制产品身份与合规底线，与"当前 55 部长什么样"无关。
几何不变量（间距 50px、不重叠、不溢出）断言的是几何事实。原先是靠人眼在每一部上重新满足的。
阅读预算 15 字/秒量化了"观众读不读得完"，与内容无关。旧片的 31 字/秒正是因为当时只检查了几何。
draft 状态严格更弱的状态（渲染不出来），不是绕过闸门的后门。
测试断言不变量而非内容25 条布局测试基本都是性质断言。抽查未发现"锁死某段文案"的写法（除上面已修的那处）。

TAX灵活性税的来源

测试 2121 行守 3529 行实现，测试:实现 ≈ 0.60。这个比例本身不算异常，问题在于改共享引擎的成本 = 改引擎 + 改测试 + 重渲染验证。

所以真正的杠杆不是删规则，而是 B（让容量按片可放，并给偏离一个留痕的地方） 和 C（给内容 schema 一个扩展点）：前者决定"长条目还能不能做"，后者决定"新形态要不要每次动引擎"。两项做完，"过拟合"就不再等于"没法表达"。

按实测的紧迫程度排序：B > C。B 那条线（约 78 字原文）现在就在切语料，9 条已经过不去；C 是形态问题，下一部要做的紫芝仍在现有形状内，可以等一个真实的新形态出现再动。
