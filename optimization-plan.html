PART 1本轮新发现

P0N1 · 布局引擎修好了"装不下"，没修"读不完"
实测

用新引擎规划一部 176 字的黄芝（原文 32 字 + 今译 56 字 + 注释 69 字 + 免责行 16 字），结果：

场景时长中文可见字符阅读速度
首屏 hero4.8 秒112.3 字/秒（空转）
中段 classical5.5 秒23242.2 字/秒
收尾 closing4.7 秒439.1 字/秒
全片15 秒17611.7 字/秒

而 findOverflow、findOverlaps、findPacingProblems 全部返回空——这部片子会以 ok 通过检查门并渲染上线。

根因
  • findOverflow 只检查块底边是否越过 1920 − 96 = 1728px，与阅读时长无关。
  • requiredDuration 的阈值（≤130 字 → 12 秒、≤220 字 → 15 秒、其余 18 秒）折算下来是 10–15 字/秒，是舒适速度的 2–2.7 倍。
  • splitTranslation 只在几何溢出时触发，所以"文字挤在一屏"永远不会触发分屏。
  • 结果是阅读负荷全部堆在中段一屏：首屏 11 字 / 4.8 秒，中段 232 字 / 5.5 秒，负荷相差 18 倍。
方向

把"阅读预算"做成独立于几何的度量，并进 checkPlan：见阶段一任务 1.2 / 1.3。

P0N2 · 冻结名单把合规风险留在了线上
实测

npm run check -- --verbose：55 部 frozen 每部 5 项 已知合规缺口（ginseng-first-film 另有 3 处片内重复短语），而它们全部是已发布状态。

判断

冻结在工程上是对的——母版就是线上副本，不回改。但它把"这些片子仍然带着触发处罚的表述挂在平台上"这件事，变成了一个只有代码注释知道的事实。账号还在养号重建期，这是当前最大的未处置风险。

方向

建一份存量处置清单，逐条决定 留 / 转私密 / 重制，并作为日后平台问询时的举证材料。见阶段一任务 1.4。

P0N3 · 选题仍按原序，发布侧没有排期
实测

已完成 54 部中 51 部属卷一·上经，其中 16 部是矿物（丹沙、云母、玉泉、石钟乳、涅石、硝石、朴硝、滑石、空青、曾青、禹余粮、白石英、紫石英、白青、扁青…）。全台账 143 / 110 / 103（上/中/下经），待办 300。

new-film.ts 支持 --entry= 跳选，但默认取首个 todo，且没有任何文件记录"发布顺序"。

判断

SKILL.md 已经写明"原序是内部生产规则，不是观众向的文案"——这条区分在文档里存在，在产品里没有落地。矿物条目同时踩三个坑：无搜索需求、画面全是分不清的石头、正撞平台判罚的"功效"高危区（upload/_incidents.md 自己也已决定"矿物功效集与雄黄暂缓"）。

方向

生产按原序不漏，发布另排一版顺序：高认知药材前置，矿物打包成合集、单期只放一条。见阶段二任务 2.1。

P1N4 · 台账有字段，没有数据
实测

upload/<kebab>.md 的 7 个必填字段（film: / 标题 / 描述 / 话题 / BGM / 抖音 / 视频号）全是文案与发布状态。台账总数：1 份（黄芝）。

判断

字段设计停在"可追溯"，没到"可迭代"。养号期最需要的是"哪类条目有效"的信号，而现在没有任何采集点——两周后仍然只能凭感觉决定下一批 30 条做什么。

P1N5 · 人格、封面、音频仍是原样
实测
  • 音频：public/music/ 只有 2 首，55 部轮播。
  • 人格：无口播、无出镜、无固定署名台词，片尾无连载钩子。
  • 封面：首帧同时承担"信息流封面"和"内容首屏"两个职责，缩略后认不出主题。
  • 标题：SKILL.md 已要求句式多样，但无"搜索词"意识。

这三项都不需要动代码管线，属于纯内容决策——也正因为如此，它们在重构中被完整地漏掉了。

P0N6 · 语料里有 17 个条目名是残缺的，按原序做会直接踩上
实测

逐个核对 000-神农本草经.txt 的 <篇名> 与内容行首句，发现 17 个条目的名字被截断：青（内容写「巨胜苗也」、《吴普》曰「青襄」→ 应为青蘘）、木（「一名檀桓」→ 檗木）、本（「一名鬼卿」→ 藁本）、石（「一名固羊石」→ 礬石）、蓬（「一名复盆」→ 蓬蘽）、蓄（→ 萹蓄）、萆（→ 萆薢）、耳实（→ 枲耳实）、发（→ 发髲），以及 青琅、兰茹、蜀菽、秦菽、浓朴、元参、麻贲。

更糟的是 KT 这个条目：内容行里写着「案∶《说文》云∶KT，菜也，叶似韭」——名字本身就是编码残缺。

影响

progress.json 只是索引，名字错了不影响进度统计，但片名、标题、话题、拼音全是拿这个名字生成的。按原序默认取首个 todo，第一条就会撞上黄芝之后的这些条目。另外 附∶《吴氏本草》十二条 和 附∶诸药制使 是附录章节，根本做不成"一味药"的片子。

方向

已在 publish-plan.md 里列成核对表；每开一条新片先 rg 核对全名写进 entry，两条附录建议标为 skipped。

PART 4风险与取舍

取舍8 字/秒 是首版阈值，可能偏严

按 8 字/秒 反推，12 秒只能承载约 96 字——比现在的译文短不少，意味着今译必须更精炼、或更多条目要分到 15/18 秒。这是有意的：宁可让译文短，也不要让观众读不完。

校准方式：先按 8 落地，两周后用台账的完播率数据回看。若完播率不降，可放宽到 10；若明显下滑，说明分屏比压缩更合适。

风险拉长到 15/18 秒可能压低完播率

时长与完播率在短视频里是反向指标。当前 55 部多为 12 秒，一旦新片普遍变成 15–18 秒，完播率可能下滑，而算法权重里完播占比很高。

对策：用同一条目做 A/B（12 秒精简版 vs 18 秒完整版），用 2.3 的数据列对比，而不是靠判断。

风险标为"留"的存量影片仍带旧表述

处置清单里选择"留"的影片，其 5 项合规缺口不会消失。若平台再次判定，处置清单是唯一能证明"已识别、已分级、已处置"的材料。

对策：清单里每条"留"都必须写一句保留理由（如"文化向、无功效陈述"），避免变成一份没有依据的名单。

方式可行性成本与风险
逐条手填 可行 每条每周约一分钟。条目一多就必然停更——这正是不推荐它的理由

下一步要做的只有一件事：给一份导出样例

从抖音创作者中心和视频号助手各导出一次作品数据（CSV 或 Excel 都行），丢给我。我会：

  • 按真实列名写 npm run stats -- --file=<导出文件>，按标题匹配到对应台账，把一行追加进「数据回填」表；
  • 把两个平台的列名差异收敛到一处映射，换平台不用改脚本；
  • 匹配不上的行单独报出来，不静默丢弃。

在拿到样例之前，「数据回填」表的表头已经就位（upload-ledger.test.ts 断言它存在），表头固定、按日期追加行，人工填也能用。
